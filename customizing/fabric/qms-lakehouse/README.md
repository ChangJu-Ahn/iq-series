# QMS 가상 데이터 시드

제조 현장의 품질관리(QMS) 데이터를 Microsoft Fabric 레이크하우스에 만들어 넣습니다.
데이터는 Mock MES를 실시간으로 조회해 그와 정합되도록 생성됩니다.

## 무엇이 만들어지나

8개 Delta 테이블, 합계 1,004행입니다.

| 테이블 | 행수 | 내용 |
|---|---|---|
| `qms_defect_code` | 24 | MES 상위 불량코드 6종을 전개한 QMS 세부 불량코드 |
| `qms_inspection_spec` | 108 | 제품·공정·특성별 검사 기준과 규격 |
| `qms_inspector` | 15 | 검사원. MES 작업자와 별개 인력 |
| `qms_inspection` | 207 | 공정검사·재검사·출하검사·공정능력조사·설비검증 |
| `qms_measurement` | 260 | 규격 대비 실측값 |
| `qms_incoming_inspection` | 200 | 자재 입고검사 |
| `qms_nonconformance` | 95 | 부적합 보고서 |
| `qms_disposition` | 95 | 부적합 처리 결정 |

## MES와의 관계

두 시스템은 별개입니다. 외래키가 아니라 `lot_id`, `product_code`, `step_code`,
`material_code` 라는 비즈니스 키로만 이어집니다. 같은 사실을 양쪽이 중복해서 갖지
않으므로 QMS에는 `mes_result`, `scrap_qty`, `operator`, `in_qty`, `out_qty` 컬럼이
없습니다. 생산이 어떻게 됐는지 알고 싶으면 MES에 물어야 합니다.

이 데이터에는 두 시스템을 함께 조회해야만 풀리는 상황이 13건 의도적으로 심겨 있습니다.
자세한 내용은 `data-agent-schema.md`를 보세요.

## 실행

### 1. MES API 키 준비

노트북 파라미터 셀의 `MES_API_KEY`에 키를 넣습니다. 작업 영역이 공유될 수 있고
Fabric 노트북은 자동 저장되므로, 실행이 끝나면 지우고 저장하세요.

Fabric 데이터 파이프라인으로 돌린다면 그 셀에 `parameters` 태그가 붙어 있으므로
Notebook 액티비티에서 런타임에 값을 넘길 수 있습니다. 그러면 노트북에는 키가
남지 않습니다.

### 2. 노트북 빌드

```bash
python3 build_notebook.py
```

`qms_lakehouse_seed.ipynb`가 생성됩니다. `src/` 모듈이 셀로 인라인되어 있어
파일 업로드나 `pip install` 없이 단독 실행됩니다.

### 3. Fabric에 업로드하고 실행

노트북을 업로드한 뒤 **오른쪽 패널에서 대상 레이크하우스를 Attach** 합니다. 적재
위치는 이 Attach 로 정해집니다. 파라미터 셀에 레이크하우스 이름을 적는 자리는 없습니다 —
`saveAsTable`에 `이름.테이블` 같은 2단 이름을 주면 Spark가 그것을 `스키마.테이블`로
해석해 실패하기 때문입니다. 스키마 사용 레이크하우스라면 `TARGET_SCHEMA`만 채웁니다.

그다음 전체 실행합니다. 고정 시드와 `overwrite` 모드를 쓰므로 같은 MES 스냅샷에서는
몇 번을 다시 돌려도 같은 결과가 나옵니다.

다만 **MES 시각 자체는 고정이 아닙니다.** Mock MES는 컨테이너가 다시 뜰 때 데이터를
그 시점 기준으로 새로 만듭니다. 실측해 보면 5분 간격 조회에서는 앵커가 그대로였지만
20분 뒤에는 20분 이동해 있었습니다. 그래서 시각 컬럼은 실행 시점에 따라 통째로
움직입니다. ID·판정·수량 같은 나머지 값은 시드가 같아 그대로입니다.

이게 QMS 시각을 MES에서 유도해야 하는 이유입니다. 날짜를 적어 두면 MES만 움직이고
QMS는 남습니다.

노트북은 적재 전에 13개 항목을 검증합니다. 고아 키, MES 중복 컬럼, 내부 참조 깨짐,
타임존 통일, 시각 컬럼 분류, 미래 완료 사건, 검사원 자격, 계측 규격 복제는 치명이라 실패하면
적재하지 않고 중단합니다.

### 실행 시각을 FDC와 맞추세요

Mock MES는 조회 시점을 기준으로 데이터를 만듭니다. QMS와 FDC를 **연달아 실행**하면
문제가 없지만, 사이에 시간을 두면 두 시스템이 서로 다른 MES를 봅니다.

FDC 쪽에서 `eqp_id` + 시각 범위 조인의 정확도를 실측한 결과입니다.

| 실행 간격 | 맞게 찾음 | 못 찾음 | 틀린 로트를 답함 |
|---|---|---|---|
| 30분 | 96% | 4% | 0% |
| 60분 | 53% | 47% | 0% |
| 4시간 | 0% | 62% | **38%** |

30분까지는 대부분 무해합니다. 네 시간을 넘으면 성격이 바뀌어, 못 찾는 대신 **엉뚱한
로트를 확신 있게 답합니다.** 어긋난 폭만큼 밀린 자리에 다른 생산 이력이 있기
때문입니다.

QMS는 8개 테이블을 매번 통째로 `overwrite` 하므로, 다시 돌리면 그 시점 MES에 맞춰
전체가 새로 맞춰집니다. 어긋났다고 느끼면 두 노트북을 연달아 다시 돌리면 됩니다.

### 시각은 전부 MES에서 유도됩니다

QMS에는 날짜 상수가 없습니다. 모든 시각의 기준점은 MES 공정이력의 마지막 종료
시각(`mes_anchor`)이고, 나머지는 거기서 상대적으로 만들어집니다. MES 앵커가 배포
시점에 평가되므로, 벽시계 상수를 두면 MES를 재배포할 때 QMS만 제자리에 남아
출하검사가 생산 시작보다 앞서는 상태가 됩니다.

앵커는 기준점인 동시에 **데이터의 "지금"** 입니다. 판정이 끝난 검사, 종결된 부적합,
내려진 처리 결정은 앵커를 넘지 않습니다. 넘게 되면 아직 오지 않은 날짜에 완료된
사건이 생기고, 참가자가 "최근 검사 결과"를 물었을 때 미래의 합격 판정이 돌아옵니다.
반대로 조치 기한(`due_date`)과 유효성 점검 예정일은 아직 오지 않은 일이므로 미래에
둡니다. "기한이 임박한 미결 부적합"이 여기서 나옵니다.

출하검사는 전역 날짜가 아니라 **로트별 생산 완료 시각**에서 유도합니다. 아직 생산
중인 로트에는 출하검사가 없어 "출하검사 대기 로트"가 자연히 생깁니다.

검사원 자격은 3년 주기로 갱신됩니다. 취득일에 3년을 한 번만 더하면 오래 근무한
사람일수록 만료 상태가 되어, 자격 없는 검사원이 수행한 검사가 대량으로 생깁니다.
실제 QMS에서 이는 그 자체로 중대 부적합이라 데이터가 앞뒤로 맞지 않습니다.

모든 `TIMESTAMP` 값은 tz-aware UTC입니다. naive 시각이 섞이면 PySpark가 그것만
드라이버 로컬 타임존으로 저장해, 적재는 성공하는데 일부 행의 값만 밀립니다.

앵커가 어디로 가든 **시각 말고는 아무것도 달라지지 않습니다.** 검사원 배정, 판정,
측정값은 앵커의 위치와 무관합니다. 두 참가자가 한 시간 차이로 노트북을 돌려도 같은
답을 봅니다. 이건 저절로 되지 않았습니다. 정기 검사 시각을 근무조 시간대에서 고를 때
후보 개수에 따라 난수 소비량이 달라져, 앵커를 한 시간만 옮겨도 검사원 39건과 판정
2건이 뒤바뀌고 있었습니다. 앵커를 정수 일수로 옮기면 시(hour)가 그대로라 후보 집합도
같아서, 27일 이동만 검사하던 테스트는 이것을 통과시켰습니다.

미래를 막는 방법도 시각 분포를 망가뜨릴 수 있습니다. 앵커 직전에 끝난 공정의 검사를
앵커로 **자르면** 잘린 것들이 앵커 한 점에 쌓입니다. 실제로 IPQC 2건과 IPQC-RT 3건이
같은 초에 놓여 있었고, 그것이 데이터에 있던 시각 중복의 전부였습니다. 지금은 자르는
대신 남은 시간 안으로 접어서 각자 다른 시각에 놓습니다. 앵커에 정확히 놓이는 검사는
그 공정이 앵커에 끝났을 때 하나뿐입니다.

> 뭉침을 "같은 시각이 하나도 없어야 한다"로 검사하면 안 됩니다. 검사 시각은 유한한
> 분 단위 격자에서 고르므로 생일 문제로 충돌이 확률적으로 납니다. PCS 36건이
> 1,440개 자리에서 무충돌일 확률은 64%뿐입니다. 우연한 충돌은 한 시각에 2건이고
> 자르기는 34건을 쌓으므로, 그 사이를 포아송으로 유도한 한계치로 가릅니다.

> **MES를 재배포하면** `tests/fixtures/mes_snapshot.json`을 다시 떠야 합니다.
> 픽스처는 오프라인 테스트의 기반일 뿐이고 노트북 실행에는 쓰이지 않으므로,
> 재배포 직후에도 노트북은 실 MES를 조회해 정상 동작합니다. 재생성은 아래
> 명령 한 줄입니다.
>
> ```bash
> MES_API_KEY=... python3 -c "import json;from src.mes_client import MesClient;\
> print(json.dumps(MesClient(BASE_URL, __import__('os').environ['MES_API_KEY'])\
> .fetch_snapshot().to_dict(), ensure_ascii=False, indent=2))" \
>   > tests/fixtures/mes_snapshot.json
> ```
>
> 픽스처가 낡았는지는 `python3 -m pytest -q` 로는 알 수 없습니다. 테스트는
> 픽스처의 절대 시각이 아니라 앵커 대비 관계만 단언하기 때문에, 낡은 픽스처
> 위에서도 전부 통과합니다. 대신 `tests/test_time_axis.py` 가 앵커를 옮기고
> 폭을 바꿔 가며 돌려 보므로, 실제 MES가 어떤 분포로 오든 생성기는 따라갑니다.

## 개발

```bash
python3 -m pytest -q                 # 오프라인 테스트 전체
MES_API_KEY=<키> python3 -m pytest -m live -q   # 실 MES 접속 테스트
```

**돌연변이로 검증할 때는** 노트북 최신성 검사를 빼고 도세요.

```bash
python3 -m pytest -q -m 'not live and not stale_artifact'
```

`test_written_notebook_is_valid_and_current`는 `src/`를 한 글자만 고쳐도 실패합니다.
노트북이 생성물이니 맞는 동작이지만, 돌연변이를 넣으면 무해한 주석 한 줄에도
`1 failed`가 나와 불변식이 잡은 것과 구별되지 않습니다. 실제로 계측 산포를 12배로
키운 돌연변이가 이 검사 하나만 실패시켰고, 하마터면 잡혔다고 읽을 뻔했습니다.
돌연변이를 되돌린 뒤에도 `build_notebook.py`를 다시 도세요. 안 하면 돌연변이가 박힌
노트북이 남아 다음 검증이 엉뚱한 곳에서 실패합니다.

오프라인 테스트는 `tests/fixtures/mes_snapshot.json`에 저장된 실 MES 스냅샷 위에서
돕니다. MES가 바뀌면 스냅샷을 다시 뜨고 live 테스트로 기대값을 갱신하세요.

`src/`가 원본이고 노트북은 빌드 산출물입니다. 노트북을 직접 고치지 마세요.
`src/`를 고치고 `python3 build_notebook.py`를 다시 실행합니다.
